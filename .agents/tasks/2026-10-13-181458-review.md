# SolarFlow MVP — Final Review

SolarFlow is an AI-powered greenhouse management system featuring a FastAPI backend, a React/TypeScript frontend, SQLite persistence, a Random Forest forecasting service, and reactive/predictive control modes. All core requirements from the spec are structurally present. The implementation is largely solid with 72/72 tests passing, strict hardware allowlist enforcement, and honest forecasting metrics. One confirmed schema mismatch between the backend and frontend analytics interface will render the Analytics comparison table non-functional at runtime.

**Watch for:** `AnalyticsSnapshot` frontend type declares `recorded_at` and `num_alerts` fields that do not exist on the backend response — confirmed mismatch. `avg_response_time_seconds` is `float | None` on the backend but called with `.toFixed(1)` on the frontend without a null guard.

**Verdict**: NEEDS_CHANGES

---

## High-level view

All 7 dashboard pages (Overview, Monitoring, Predictions, Alerts, Automation, Analytics, Device Health) are routed and sourced. All 10 API endpoints from the spec are implemented across the router files and registered in `main.py`. The hardware allowlist in `hardware.py` enforces exactly `{"fan_on", "fan_off", "noop"}` with a `ValueError` raised before any I/O — confirmed. Forecasting metrics are computed via a strict chronological 80/20 split in `train_models()` — not fabricated, with `is_validated=False` on all synthetic-trained predictions. No TypeScript `any` types appear in any frontend source file. Both LiveChart and ForecastChart include `ReferenceLine` components for temperature and humidity thresholds. Simulated data is labelled in the Header badge, the Monitoring table source column, and the ForecastChart synthetic banner. Reactive and predictive control modes use structurally distinct logic in `ControlEngine._reactive_decision` and `_predictive_decision`, with predictive falling back to reactive explicitly when no forecasts are available. All 72 pytest tests pass.

The Analytics page has a confirmed schema mismatch: the frontend `AnalyticsSnapshot` type declares `recorded_at`, `num_alerts`, and `period_hours` fields that are absent from `AnalyticsSnapshotOut`. The backend model uses `captured_at` (no alias) and has no `num_alerts` column. The `ComparisonChart` summary table accesses `num_alerts` at runtime and will render `undefined` for both reactive and predictive rows. Additionally, `avg_response_time_seconds` is `float | None` in the backend but called as `.toFixed(1)` in the table without a null check.

## Analytics schema mismatch and missing writer

The frontend `AnalyticsSnapshot` interface in `types/index.ts` declares three fields that have no counterpart in the backend: `recorded_at` (backend sends `captured_at`), `num_alerts` (no column in `AnalyticsSnapshot` model or `AnalyticsSnapshotOut`), and `period_hours` (same — absent from model and schema). The `ComparisonChart.tsx` summary table accesses `reactive?.num_alerts` and `predictive?.num_alerts` and will produce `undefined` for both cells at runtime, silently producing a broken table rather than a visible error.

The more fundamental problem is that no code writes to the `analytics_snapshots` table. The scheduler tick in `main.py` calls `evaluate_reading`, `evaluate` (control engine), and the forecasting service, but never generates an `AnalyticsSnapshot` row. Until a writer exists, the analytics endpoint will always return an empty list regardless of how long the system has been running.

`avg_response_time_seconds` is typed `float | None` in both the model and `AnalyticsSnapshotOut`, but `ComparisonChart.tsx` calls `.toFixed(1)` on it directly. This will throw `TypeError` when the backend returns `null`, which is the default for a newly created row.

</details>
